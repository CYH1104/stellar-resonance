# 头像尺寸与竖向构图纠正

基线 8853f47；此文覆盖上一份交接中“26/34/48px、横向长方形、统一512方形裁剪”的说明。上轮对用户要求理解错误：用户要显示面积和原图可见范围随尺寸增加，长方形是竖向。

## 根因及修正

- 原先仅缩放同一张方形裁剪图，且对话优先读取裁剪图，无法恢复被裁掉的内容。现在对话优先读取完整 portrait，并按当前尺寸的构图显示。无原图、仅有旧裁剪图时保留回退，不虚构缺失内容。
- 显示尺寸小/中/大为48/96/160px宽；正方形和圆形等宽高；竖向长方形高度为宽度1.4倍，即48×67、96×134、160×224。预览与对话共用UserAvatar，避免编辑区和实际显示不一致。
- 小号默认放大取景，中号减少放大，大号默认 contain 展示完整原图，绝不先统一裁成正方形再放大。圆形仍受圆形轮廓遮罩；图片自身比例与轮廓不同时保留背景，不拉伸原图。
- 各尺寸独立保存zoom/x/y；可拖动、缩放和恢复当前尺寸默认构图。未使用人脸检测，具体脸部位置由用户拖动决定，默认取景不能替代针对任意图片的人脸定位。
- 编辑画布随竖向形状变为200×280；大号预览实际160×224。修复预览纵向flex布局误用宽度作flex-basis导致高度缩水。异步图片加载与构图导出使用独立版本号，防止切换尺寸/图片时旧结果覆盖新设置。
- 原图始终保留，现有avatar字段继续作为兼容导出图；竖向导出保留竖向比例。构图随原有人设档案自动保存，不发送模型。

## 验证

- 修改前运行 `node node_modules/vitest/vitest.mjs run tests/avatar-framing.test.ts`，尺寸和竖向比例两项均失败，精确复现此次问题。
- 修正后全量77文件400前端测试通过，类型检查和生产构建通过。最后的flex布局修正另用相关头像测试与浏览器DOM尺寸检查验证；服务端业务未修改。
- 使用实际UserAvatar与PersonaImageEditor组件，在本机忽略目录的视觉验收页加载同一张合成完整人物PNG，对照九种组合；验证显示范围随尺寸扩大、竖向比例、尺寸独立构图、小号1.91缩放切换大号仍为1再切回保留1.91。
- 验收页只用合成测试图片，不包含玩家图片或存档，不上传仓库。已确认真实预览48×67，布局不会被压回方形。
- 真实照片构图仍需用户按喜好调节；没有额外模型请求。本轮按用户既有授权上传main并部署，实际提交/备份/健康检查结果在Slack汇报。
