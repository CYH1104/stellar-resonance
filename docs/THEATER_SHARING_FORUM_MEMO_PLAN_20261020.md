# 小剧场分享码、论坛多回复、提示词保护、人设备忘录

日期：2026-10-20。基于本地 main `e524b33` 核对。

本次用户首先要求方案。第 2 项另外明确要求“如果只有 1 条就改”，因此已修改论坛多回复的本地代码；第 1、3、4 项仅设计或调查，尚未实现。未调用真实模型，也未部署公网。

## 1. 每个自定义小剧场生成短分享码

### 方案

采用“服务器保存模板，短码查模板”，不把完整模板压进短码。模板可能有数千字，纯字母数字的离线自包含编码不可能一直很短。

- 每个自定义位置增加“生成分享码”，生成前预览将分享的名称、类型、模板类别和内容要求。
- 分享码建议为 10 位随机字母数字，例如 `T7mQ4x2K9a`，由服务器安全随机生成，碰撞时重试。示例不可实际导入。
- 分享的是生成规则，不是已经生成的日记、同人文、正文、聊天记录、人设或 API 配置。
- 每份分享记录带协议版本，发布为不可变快照。后续编辑本地小剧场不会偷偷改掉别人已经导入的内容；重新分享产生新版本或新码。
- 作者可撤销分享码；已导入的本地副本保留，后续再导入会显示失效。
- 短码不是加密或私密权限，知道码的人可以查看分享的模板。生成前明确提示，不能让用户误以为模板仍保密。

### 导入

小剧场设计页增加“导入分享码”：输入 → 服务器查询 → 预览 → 新增到空位置或用户明确选择替换 → 保存。默认关闭，不自动调用模型，也不覆盖论坛位置。

导入校验名称、长度、类型、模板标识和协议版本，只接收允许字段。绑定角色不能盲目照搬：目标角色无法识别时，让用户重新选择搭档或改成按场景选择。不执行导入内容中的 JavaScript，也不导入任意脚本/正则执行权限。

### 服务端

- 建议接口：`POST /api/theater-shares` 创建，`GET /api/theater-shares/:code` 查询，作者授权后撤销。
- 记录包含代码、模板快照、版本、作者账号、创建时间和撤销状态。与私有运行数据一起落在服务器持久存储，不存前端构建产物里。
- 沿用账号认证，创建与查询增加限流及大小校验；采用原子写入和唯一代码约束。
- 分享码默认只在同一套服务器部署中有效。跨站点或离线交换另保留模板 JSON 导入/导出，不能声称短码脱离服务器也通用。

### 验收

生成、预览、导入、重复导入、撤销、未知代码、非法内容、陌生角色映射、服务器重启后读取均验证；分享内容中没有 Key、人设或聊天数据。

## 2. 星际论坛：玩家评论后至少 5 条回复

### 代码核查结果

原实现是一次论坛接口调用返回一个 `{authorId, authorName, content}`，服务器随机选一名角色或“校园路人”。没有以楼主、原评论者和玩家点名角色组织多人回复。

### 本地已修改

- 新版工作区请求带 `minReplies:5`，同一次论坛模型请求返回 `replies` 数组。
- 成功结果为 5～50 条有效回复；不意味着必须由 5 个不同人物发言。同一人物可以有内容不同的后续回应，不能拿重复文字凑数。
- 候选发言人包含楼主、已有评论者、服务器已登记角色。前端单独传入原评论者姓名，避免只截取最近 12 条上下文就完全失去旧路人身份。
- 楼主、近期已有评论者和明确点名且可识别的角色作为必需发言人；其他相关角色由模型结合公开帖子和讨论内容选择。没有相关性时不能强行让全部角色发言。
- 发言人的 ID 和显示名由服务器映射；不允许模型随便编 ID 或冒充玩家。人物是否与话题真正相关，仍需真实模型验收，程序不能靠格式校验保证语义正确。
- 整组返回后校验数量、身份、必需发言人、重复内容和格式；少于 5 条、遗漏必需人物或截断时明确失败，不自动追加付费调用或伪造填充文字。
- 整组预校验后写入，同组绑定同一条玩家评论；重复送达、重复补取不追加第二组。沿用每帖 100 条本机评论容量限制，容量不够时保留玩家评论并提示。
- 成功显示实际条数；失败保留玩家评论，允许手动重试。评论回复不改主线变量或主线记忆事实。
- 保留默认关闭的论坛 AI 回复开关及现有接口选择。开启后每条玩家评论额外调用一次论坛接口，不是每条 NPC 回复各调用一次。
- 旧客户端不传 `minReplies` 时仍兼容单条返回；新版页面实际走的是至少 5 条模式。

### 主要修改位置

`server/forum.mjs`、`server/app.mjs`、`src/gateway/http.ts`、`src/app/useWorkspace.ts`、`src/domain/story.ts`，以及 API 设置中的说明文字。

测试覆盖名单构造、至少 5 条、缺必需人物、重复文本、未知作者、截断、一次 HTTP 请求只调用一次上游、整组原子写入、重复提交防重、备份恢复及工作区实际请求路径。

本地验证：前端/领域 352 项通过；服务端全量 295 项通过，最终论坛与 HTTP 相关 41 项再次通过；类型检查与生产构建通过。修正了两条原有记忆页测试只接受无 Vue scoped 属性的脆弱 HTML 匹配，没有修改记忆页业务逻辑。本地服务已重启到本轮代码，地址仍为 `http://127.0.0.1:8817/terminal`。尚未使用真实模型验证发言相关性与人物表现，代码未提交或推送。

## 3. 询问服务器内置提示词时自动拒绝

### 当前调查结论

在当前源码的生成路由、论坛路由及相关提示词组装中，没有找到独立的“识别索要服务器内置提示词 → 调用模型前拒绝”的通用检测器。

现有权限隔离、私有文件不直接提供、隐藏推理过滤，以及部分提示词中的保密要求，都不能等同于这类意图监测。外部模型可能自行拒绝，也不能算网站已实现监测。

### 建议方案

1. 在服务端建立统一输入检查，先覆盖剧情、续写/补全、论坛、人设辅助、随机事件等用户可触发的模型入口；记忆和辅助入口同样梳理调用边界，不能只给聊天框加检查。
2. 对明确要求“原样输出系统提示词、导出服务器隐藏规则、忽略规则后泄露内部消息”等高置信请求，在调用上游前直接返回 `PROMPT_DISCLOSURE_REQUEST_BLOCKED`。
3. 只检查应当被当作玩家请求的内容，不能把服务器自己附加的保密规则反过来误判。正常剧情、用户自己的预设编辑和“提示词怎么写”不应只因含关键词就被禁止。
4. 所有模型入口统一加保密约束；输出补充敏感标记/明确秘密片段检查。流式输出不能先把秘密发送给浏览器，再在结束后声称已拦截；如做输出拦截，需设计发送前缓冲。
5. 拒绝只记录安全类别和必要来源，不向普通玩家暴露检测规则、私有提示词或密钥；不因此更改状态或新增主线记忆。

### 保密边界

关键词或正则检查不能保证理解所有绕过表达，也不能保证模型不泄露改写后的信息。

尤其是：如果玩家可填写自己控制的模型 API 地址，服务器组装的私有提示词就可能直接随请求到达玩家服务器，根本无需在聊天里诱导模型输出。若要求内置设定真正不交给玩家控制的服务，就必须限制接收私有上下文的接口为服务器认可的服务，用户自定义接口不能接收这些私有内容。极敏感秘密不应进入模型上下文。

## 4. 人设档案增加独立人设备忘录

### 当前状态

已有“其他”人设文本，但没有独立备忘录。人设档案当前由 `PersonaLibrary` 保存到按账号作用域隔离的浏览器 IndexedDB，不能把它称作已经上传服务器保存。

### 建议第一版

- 每份人设档案增加“人设备忘录”折叠区，用来记录作者想法、待补设定和使用提醒，建议最多 2 万字。
- 单独存为档案元数据 `PersonaFile.memo`，不塞进 `Persona.other`；旧档案默认为空。
- 随“保存人设”保存，切换档案提示未保存内容；复制为新人设时复制一份独立备忘录，后续互不影响。
- 默认不发送给模型，不改变状态变量、不加入向量记忆，也不被“AI 帮我写人设”覆盖。
- 以后如要给模型使用，可增加玩家明确选择的“将选中内容作为本轮提示”入口，不能默默把全部私人笔记发出去。
- 人设文件导出默认不包含备忘录；若提供备忘录导出，使用独立选项并清楚说明。备份/恢复也要覆盖这份档案元数据，不能只备份聊天存档就宣称笔记已备份。
- 如果后续改成服务器同步，另做账号归属检查和同步策略，不能仅靠前端显示隔离。
