# 状态栏与 MVU 参考结构研究

日期：2026-10-18。参考用户本地提供的《养小孩模拟器.json》。仅静态阅读配置及内嵌脚本，未执行角色卡代码，未下载其外部模块，不导入其角色、剧情或数值体系。本文是研究与后续实现建议，不表示项目已经接入 Zod 或兼容该卡全部功能。

## 参考卡的实际分层

| 层 | 配置位置 | 职责 |
| --- | --- | --- |
| 初值 | 世界书 `[initvar]变量初始化勿开` | 初始化身份、时间、数值、动态字典；该条目当前禁用，不能仅凭存在推断运行时一定执行 |
| 业务规则 | `[mvu_update]变量更新规则` | 描述变量何时能变、变多少、哪些变化必须同时发生 |
| 当前状态注入 | `变量列表` | 用 `{{format_message_variable::stat_data}}` 提供上轮已提交状态，避免重新累计旧剧情 |
| 更新协议 | `[mvu_update]变量输出格式` | 每轮末尾输出一个 UpdateVariable，内部 JSONPatch 数组 |
| 变量引擎 | `extensions.tavern_helper.scripts` 中 MUV 脚本 | 导入外部 MagVarUpdate 引擎；仅看此 JSON 不能确认引擎全部执行语义 |
| 类型规则 | 同目录的“变量结构”脚本 | 定义 `z.object`，调用 `registerMvuSchema(Schema)`；数值转换、边界、枚举、默认值及动态对象结构 |
| 展示 | `extensions.regex_scripts` | 识别角色资料、状态栏、菜单等标签，替换为 HTML 展示模板 |

特别关键：状态栏允许模型只输出空的 `<characterstate></characterstate>`。模板中的脚本等待 Mvu 初始化，通过 `getAllVariables().stat_data` 读取状态，填入面板，而不是依赖模型逐项手写完整状态 HTML。活动菜单同样从变量构建。

## 变量结构的设计方法

这份卡把变量分成相对固定的身份字段、时间与进度、有限范围数值、动态等级词条、系统追踪、NPC 关系字典、事件去重记录。

可借鉴的是分类方式：固定字段只允许特定情节修改；连续数值有范围；枚举限定可选状态；NPC/任务用动态字典；已触发事件独立记录。不要复制其姓名、世界设定、年龄系统或具体上下限。

“变量结构”使用字符串/枚举、数值强制转换、变换截断、prefault 默认值，以及 z.record 或 catchall 描述动态键的值结构。这些声明能约束结构，但不能自动验证剧情是否真的支持某次好感变化。

## 捕获与展示规则

- 展示规则用跨行匹配识别 `<characterstate>`、`<actionmenu>`、`<character-info>` 等块，角色资料有外层、内层两次替换。
- UpdateVariable 完整块和未闭合流式块分别有展示替换规则，显示完成/处理中；这只是展示提示，不代表变量一定成功写入。
- `promptOnly` 规则清除历史更新块，降低重复发送补丁导致重复计算的风险；另外注入当前状态作为计算基准。
- 显示替换和发送前替换是两条不同通道，不能先清掉更新块，再尝试解析补丁。
- 参考卡的模板主要在初始化时读取变量；是否自动随同一轮后续补丁刷新，还取决于酒馆运行时与外部引擎，不能仅凭该配置保证同步正确。

正则只定位外层边界，不用来解析任意嵌套 JSON。捕获后应使用 JSON 解析器和字段校验。流式块未闭合时暂缓提交，保留正文，不把半截补丁当作成功。

## 发现的不一致

参考卡业务规则中 NPC 好感度允许 0～200，Schema 却将其截断到 0～100；规则还用到超过 100 的关系阈值。照搬会使部分阶段无法到达。

默认值、提示词、校验边界、界面读值也需要同源。缺失更新字段应沿用旧状态；不能把一段不完整的更新当成全量初始化，用默认值覆盖现有进度。类型转换只针对明确允许的字段，不能把空字符串随意当作合法数值 0。

## 与学院当前代码的对照

本次读取时，项目已有：

- `src/domain/mvu.ts`：UpdateVariable/JSONPatch 解析、路径防护、补丁操作、状态投影和角色字段校验。
- `server/ai.mjs`：状态标签定位与正文分离。
- `src/app/mvuBridge.ts`：当前变量读取、替换及 MVU 事件桥接。
- 学院状态根为 `player`、`characters`、`custom`，不等同于参考卡所有变量直接平铺的 stat_data。
- 学院角色好感度范围为 -100～100；角色 ID 集合受保护，不能照搬参考卡动态新增 NPC 的处理。
- 当前 package.json 没有 Zod 依赖；已存在的 `schema` 描述对象不等于完整 Zod 注册与执行机制。

因此应在已有解析和调用流程上补强，不能重复搭一套并行状态源，也不能说“已支持 JSONPatch”就等于完整兼容 mvu_zod。

## 学院适用的目标流程

1. 请求发送已提交的当前状态、对应字段的简短英文更新规则，以及一个合法格式示例。
2. 有独立状态副接口时，正文由主接口生成，状态接口只接收判断所需的正文、当前状态与状态规则；没有副接口时，主接口一次同时输出正文及补丁，不增加格式修复调用。
3. 先隔离正文和控制块；完整捕获后做 JSON 解析、操作与路径检查。
4. 在旧状态的副本上应用补丁，再做类型、范围及跨字段约束检查；通过后才持久化，记录楼层与版本，防止同一返回重复提交。
5. 状态栏从已经提交的变量渲染；不要求模型复制整个状态栏，也不由展示正则修改存档。
6. 失败时保留正文、旧状态和诊断，不清空整个状态，不自动重复付费请求；是否允许按独立操作保留有效部分，需要明确事务边界，不能破坏相关字段的原子更新。

学院示例只说明协议，不迁移参考卡变量：

```xml
<UpdateVariable>
<JSONPatch>
[
  {"op":"delta","path":"/characters/EXISTING_CHARACTER_ID/affinity","value":2},
  {"op":"replace","path":"/characters/EXISTING_CHARACTER_ID/present","value":true}
]
</JSONPatch>
</UpdateVariable>
```

示例 ID 必须替换为存档中已存在的角色，数字变化必须有本轮剧情依据。该协议无需返回模型思维链或分析段落；诊断可以记录字段路径、验证结果和提交结果。

下一步实现前应先确定学院可变化变量的清单、初值、类型、范围、触发条件和跨字段关系，再让提示词示例、校验器与面板共享这些定义。此阶段不改动现有存档和 API 调度。
