## 已实现的记忆改造

记忆页六张表：当前状态、人物状态、事件纪要、知情事实、约定追踪、小游戏记录。表格支持筛选、每页20条、来源跳转和完整记录展开。当前状态来自已提交剧情，不根据设备时间伪造剧情日期；人物数值仍由剧情状态管理。

事件、事实、约定可通过字段表单编辑时间、地点、参与者、玩家/角色行动、获得/失去、事实及知情角色、约定内容/期限/状态。保存复用原有格式校验；数值变化由真实状态重新计算；保留修订历史并失效旧向量。编辑守卫检查存档、记录修订与原记录内容，底层存储继续使用跨页面乐观锁；写入失败恢复编辑前的记忆。

约定以当前剧情路径的最新结构化状态为准。之前终端逐条旧记忆提取 open 约定，导致后面已经履行的约定又被当待办提取；现在先汇总最新状态，再投影检索候选；很早建立但刚更新的约定，按其最新出现轮次参与优先排序。旧事件保留在存档，切回履行之前的分支会恢复当时状态。任意自然语言里相似但未关联同一ID的约定，仍依赖逐轮整理正确识别，不能宣称所有模型矛盾已消除。

实际请求行为：
- 正文记忆最多8段，当前约定状态放在前面，约定块最多约2400字、30条；历史只是当时情况。
- 终端保留最近游戏事实及角色可知的剧情事实；当前约定有独立的小预算（最多4条、合计1400字范围内，再受事实总预算限制），不会因用户只说“继续”就完全依赖关键词命中。
- 未知/歧义角色不获得新知情权；其他分支和未完成的记忆不注入。
- 预览共用正式组装函数。可选正文/单角色终端视角，空问题只看固定上下文；填写问题执行实际检索，启用向量时可能产生一次向量请求。预览只显示记忆部分，不是完整系统提示或全部聊天上下文。
- 原始记忆、来源账本、终端历史按需展开，减少隐藏内容的DOM开销。

不新增持久化字段、数据库或localStorage设置。所有编辑仍写入现有 `Session.memories` 的 record/revision/revisions；既有 BackupArchive 采集流程继续覆盖。新表、搜索、分页、预览只是派生视图，不需要额外备份。记录修订/恢复、本地与云端往返、写入失败、跨页面冲突均有回归验证。

## 所有人的存档改存服务器，会快很多吗？

不能只按“本地/服务器”判断。IndexedDB本身提供异步、事务和索引，适合较大量本地结构化数据；它并不天然比远程数据库慢。参考： https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API

本项目之前已经定位过浏览器保存路径的重复校验和历史重放。那类CPU开销如果照旧留在前端，仅把文件改存服务器并不会消失。网络请求还会引入往返延迟；服务器要承担所有用户同时保存、检索和恢复的负载。

建议以后按测量决定：本地保存当前活跃存档和缓存；服务器保存同步副本、备份和较大历史；需要时把检索/索引或重校验计算放服务端，客户端只取必要片段。要一并设计账号隔离、版本冲突、离线编辑与增量同步。是否明显加速，要比较保存耗时、主线程阻塞、请求延迟、服务端排队、存档大小和并发负载，而不是直接承诺“全部上服务器就快”。本轮没有迁移任何存档。

## 狼人杀现状及建议规则

当前代码 `PersonalTerminal.vue` 仍将狼人杀放在 lockedGames；下面是拟实施方案，不是已上线功能，也不是对所有狼人杀版本通用的规则。基础昼夜流程参考发行方说明（白天讨论投票，夜晚狼刀/查验）： https://beziergames.com/products/ultimate-werewolf

建议先实现九人标准房：玩家1人、NPC8人；3狼人、3普通村民、预言家/女巫/猎人各1人。首版不加警长、守卫、白痴等扩展身份，减少互相矛盾的规则分支。

固定采用以下本项目规则：
1. 夜间次序为狼人选刀 → 预言家查验 → 女巫用药；程序收集动作后统一结算，不让模型自由决定谁死亡。
2. 狼队互认，只能选一名存活的非狼人为刀口；首版禁空刀、自刀和狼自爆。
3. 预言家每夜查验一名存活且非自己的玩家，程序仅返回“狼人/好人”，不返回具体神职；查验结果私有。
4. 女巫有一瓶解药、一瓶毒药；每夜最多用一瓶。允许首夜自救，以后不能自救。解药剩余时知道本夜刀口，耗尽后不再提供刀口；毒药可以选择其他存活目标。死亡在夜末同时结算，被刀女巫仍可在当晚行动。
5. 猎人被狼刀或投票出局时可开枪带走一名存活玩家，也可放弃；被毒死不开枪。开枪连锁处理完再检查胜负。
6. 天亮只公布死亡名单或平安夜，不公开死因、狼人目标、查验、药品信息；玩家自己的技能结果单独显示。出局不自动翻牌，猎人开枪会公开身份。
7. 首夜死者和白天投票出局者有遗言，后续夜晚死者无遗言；死者不能正常发言、投票、行动。
8. 白天按座位顺序发言，起点由程序公开随机确定，之后轮流。玩家轮到时等待输入，不能预先生成后面的回应。讨论结束后同步锁票，再公布投票。
9. 首次平票：平票者各补充发言一次，其余存活者从平票者中再投；再次平票或全员弃票，则当天无人出局，进入下一夜。禁止投自己，允许弃票。
10. 采用“屠边”：狼人全部出局则好人胜；3名普通村民全部出局，或3名神职全部出局，则狼人胜。夜末/投票及猎人连锁完全处理后判定；若最后狼人和最后一边同时死亡，先判断狼人全灭，判好人胜。本规则开局展示并写入对局 rulesVersion。

## API请求方案：推荐保密模式

身份和规则由程序掌管，模型只做角色决策和语言表达。

| 阶段 | 建议文本API次数 | 输入与输出 |
| --- | --- | --- |
| 发身份 | 0；可选1次公共开场 | 程序随机洗牌并保存身份，各角色每次请求固定注入自己的身份。开场请求只含公开人物设定，不给全体身份 |
| 狼队选刀 | 0或1 | 玩家为狼人时可直接代表狼队选刀，0次；否则狼队合用1次，输入狼队身份与公开信息，返回合法目标 |
| 预言家 | 0或1 | 玩家预言家自行选择，0次；NPC预言家1次选目标，查验结果由程序写入其私有记忆 |
| 女巫 | 0或1 | 在狼刀确定后请求；玩家女巫自行操作，0次；NPC女巫1次，仅收到其有权知道的刀口、药品状态和公开情况 |
| 天亮主持 | 0 | 程序按结算生成公告，不让模型改变死者名单；可选1次只润色公共公告 |
| 白天发言 | 存活NPC数 n | 每个NPC单独请求，按发言顺序串行；含自身身份/私有结果、已发生公开发言与已知记忆。玩家发言不算API |
| 投票 | n | 每个NPC单独决策，输入全部公开发言和自身私有记忆；可并发，但全部结果提交后统一公布，避免后投者偷看票型 |
| 追加发言 / 猎人 / 遗言 | 每个需要模型操作的NPC 1次 | 仅在规则触发时请求；玩家操作0次，合法目标由程序限定 |
| 终局 | 可选1次批量感想 | 程序结算与揭晓身份后，所有角色都可知道真相，此时可一次生成全员感想；各角色记忆记录参与时间、身份、胜负和关键事件 |

夜间最多 **3次独立文本请求**，可排成 **2个等待阶段**：狼队与NPC预言家并发，狼刀确认后再处理女巫。2个等待阶段不等于2次请求。人类玩家是狼/预言家/女巫并自己完成对应决策时，可降到最多2次；玩家是村民或猎人时，完整模型决策最多3次。其他技能死亡、无药等会减少次数。

首日若9人都存活、其中8个NPC，完整模式是8次发言+8次投票；有死亡则相应减少。这里统计业务成功请求，不含向量请求、失败重试、结构修复和可选润色。超时重试设置上限，不能无限补调。

白天每人一次的理由：后发言者应听到前面已经发生的发言；如果一口气生成整桌，玩家在中间插话后，后面的预生成内容就不再基于真实信息。将所有私有身份塞进一个调用、再要求模型“各自假装不知道”，也不能提供与分开请求同等的信息隔离。

## 如果优先要求夜间最多1–2次：省请求模式

可把狼人/预言家/女巫的目标选择改成**本地策略程序**，它们仍只使用该身份有权知道的信息。夜晚结算0次模型；天亮公共公告0次或一次润色。这样可以严格控制业务调用次数，但夜间选择的个性、推理能力取决于我们编写的策略，不是每个角色都由大模型现场思考。

另一种折中是1次请求同时提供狼队/预言家/女巫的全部身份和秘密，让模型当全知导演。它省调用，但无法验证各角色没有借用其他身份的秘密，**不推荐作为默认公平模式**。

我的建议：默认保密模式，夜晚最多3次/2阶段，白天逐NPC发言；另提供省请求模式，把夜间决策与最终投票改为本地策略。仍不建议把逐人发言全部合成一个带私有身份的请求。

## 身份记忆与请求可靠性

- 对局私有状态单独按角色ID存储，身份、狼队名单、个人查验、药品、私有行动仅传给拥有权限的角色；“角色记住身份”靠每次请求注入，不靠模型供应商会话自动记忆。
- 白天公共日志仅记录公开消息。局中禁止把全知身份表和未公开夜间动作写进全员的普通聊天记忆。
- 请求携带 gameId、round/day、phase、actorId、expectedRevision、requestId；响应只接受当前阶段的合法动作。旧响应、跨存档响应、重复结算丢弃。
- 首次分配先落盘再展示；重试不重发身份、不重新扣药、不重复结算。网络失败保持原阶段，可重试或由玩家明确选择程序托管。
- 模型输出严格JSON、目标白名单、状态机与胜负规则本地验证；模型不得写分数、身份或死亡结果。
- 新增对局字段时必须补齐本地下载、云端、恢复副本、旧格式、未知规则版本拒绝、分支切换、跨页面写入冲突的测试。
- 需要实测的重点：身份不串、狼刀与用药依赖、玩家中途操作、平票、猎人连锁、药品仅扣一次、末狼与末神/民同死、死亡后权限、失败重试、刷新恢复、终局记忆。
