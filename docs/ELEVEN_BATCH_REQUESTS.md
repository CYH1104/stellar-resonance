# 十一点半：每次按钮操作一次游戏请求

## 用户确认的顺序

1. 点开始游戏：程序洗牌并全员发1张，保存后一次API返回全部NPC公开台词和下一次要牌/停牌决定。缺失的酒量也由本次结果补齐，不另发tolerance请求。
2. 用户填留言（可空）并点要牌/停牌：程序合并玩家选择与上一轮已保存的NPC决定，统一发牌，内部检查11.5、爆牌和五张停牌；随后一次API按新手牌生成全部NPC回应与下轮决定。有留言须回应留言，无留言可按人设随意接话、诈唬。
3. 后续每次用户操作重复第2步。已停牌角色不发牌，仍可参与桌上聊天；玩家已停牌时点继续按钮推进。结束当轮也返回一次结果回应，不能再产生要牌决定。

公开聊天现采用[连续多条对话方案](./GAME_CHAT_AND_RISK.md)：讲话与私有决定分开，同一角色可多条、顺序打乱、低概率沉默；即便不发言，也必须有合法的私有决定。对话不再按波次标题分组。

发牌、点数、判胜、罚酒、连庄及醉酒结束均由程序裁定。邀请/重新邀请和结束后的醉后小剧场仍是原有独立功能，不计入每轮发牌的一个游戏请求。

## 信息与格式

party-eleven-batch一次接收所有NPC各自的私有手牌区段，批量决定仅供程序使用，不能在公开台词中披露。玩家未公开的手牌和真实点数不发送；按新版规则爆牌后，该人的牌面和点数已公开，可以通过严格校验后的publicTable供其他角色参考。每个NPC的决策只能依据本人区段和公开消息，公开台词支持诈唬，但不能透视他人手牌。公开文本保存前继续执行现有精确报点/牌面及心理活动格式检查。单个模型调用扮演多角色，文本检查不保证识别任意暗号或隐喻。

HTTP成功/失败均不返回模型raw；不追加自动格式纠正、逐角色review或额外公开聊天请求。未知字段、错误名单、重复牌、非法决定和不完整酒量结果拒绝，不静默保存部分数据。

## 持久化与失败

ElevenRound新增可选batch {version:1,pending,wave,playerInput,finalReplies?}。每轮发牌与玩家留言先保存，pending记录尚未收到角色回应；超时/停止/刷新后可补齐当前回应，重试不再发牌或重复罚酒。pending完成前不能开始下一局。原waves-v1和逐人旧局保留原手牌、牌堆、已停牌名单及已锁决定，不重抽；已有历史文本不重写。

batch随现有terminal.partyRooms进入本地下载、云端上传/拉取、数据库分片及覆盖前恢复副本；旧存档缺batch继续支持，未知版本或字段在导入写入前拒绝。旧客户端可能拒绝新备份，导入前更新页面。

## 发布范围

只部署9000 test实例。8807 stable和8088不修改、不重启；不运行默认双端发布脚本。测试使用合成数据和模拟上游，不消耗用户真实模型额度。
