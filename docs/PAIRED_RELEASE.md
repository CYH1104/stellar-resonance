# 8807 与 9000 共同更新

2026-11-13 用户要求：两端按最新 main 同步，8807 同样支持手机终端。不再维护“8807 关闭手机、只升级 9000”的功能差异。

- 使用同一份代码、同一次前端构建和同一个内容快照 ID。
- 保留 `stable` / `test` 实例名，仅用于原账号目录、登录 Cookie、日志、编辑器和恢复指针隔离；不能合并或复制用户账号和存档。
- 两端手机能力均开放；用户仍需配置独立终端 API 并主动开启手机。关闭手机时的请求停止、独立 API 和正文/终端顺序控制沿用既有逻辑。
- 8088 新版不在这次同步范围。

## 日常发布

原有命令现在默认同时更新 8807 和 9000：

```bash
cd /home/ubuntu/stellar-resonance
bash scripts/update-server.sh http://43.138.251.91:8807
```

也可直接运行 `scripts/update-both-server.sh`；传入同一主机的 9000 地址同样会更新两个端口。先加载原有 Node/pnpm 环境。此命令不启用定时器；当前没有定时自动更新。将来若明确启用原有自动更新器，它会核对两个实例的发布记录，不能因 8807 已更新就漏掉 9000。

只在明确的单实例故障恢复时使用 `STELLAR_SINGLE_INSTANCE_UPDATE=1`，并指定原有 `TERMINAL_INSTANCE`；该入口不用于日常发布。

## 发布与失败保护

更新前取得两个实例更新锁和共享构建锁，备份现有文件，取 main 并安装、构建一次。准备两份内容相同的固定快照，不修改私有账号目录。等待现有 HTTPS 模型连接结束，再逐个重启和核对健康身份、快照 ID、手机能力。两个端口都通过后，才确认发布并推进两个 `last-deployed-main`。

任一重启、健康检查、指针确认、记录写入或收尾失败，恢复本次已切换实例的原版本与发布记录。回退失败明确报错，保留原版本 pending 指针供恢复，不报告更新完成。`server/.local/paired-update.json` 为运维记录，不是用户存档，不进入用户下载/云端备份。

进程突然被强杀或机器断电不属于可捕获异常；若记录停在 `deploying` 或存在 pending，下一次更新会停止，需先核查两端运行版本并完成恢复，不覆盖未收尾记录。更新前等待网络连接无法阻止等待结束后新发起请求，完整后端发布仍可能短暂重连；不要将它描述为前端热更新。

## 验证

真实本地路由验证两个通道的手机能力与正文生成一致，账号目录、会话/编辑器 Cookie 仍相互隔离；后台模型由模拟接口提供，不使用客户额度。

发布故障测试使用实际临时指针/marker/pending 文件，注入第二端 pending、重启、超时类健康失败、确认和保存失败；慢健康检查期间不得提前确认任一端；还覆盖回退失败、日志保存失败及他方移动当前指针。

前端回归包含慢请求、取消、迟到结果、设置/存档及备份数据往返等已有场景。本次无新增客户端存储字段或备份格式变化，不修改人设和终端记录。Linux 自动更新器的 shell/锁测试需要在 Linux 运行，Windows 跳过不得计作通过。上线后另行核对两端公开资源、功能能力、恢复指针和数据文件完整性。
