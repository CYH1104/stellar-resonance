# 手动改写后续写通讯缓存失效修复

基线 ba3d7f704f6c6e4061185a9bdfba12f35d8c0d6a，分支 rebuild/sillytavern-native。关闭上一轮独立验收发现的 P2 后，再继续整体原生迁移；main 和 8807／9000 未更新。

## 问题与修复

正文先行生成后，完成稿的后续续写通过 continuation-context 投影继承已提交通讯。手工改正文不改变稿件 ID，旧投影曾保持 ready，导致下一次续写继续注入基于改写前正文生成的通讯事实。独立审查已在原 ba3d7f7 的单元测试和实际请求中复现。

现在仅在 editMessage 的 assistant 分支检测清理后的正文确实发生改变时，将同轮、同稿且 ready 的 continuation-context 标记为现有 failed 状态，并记录失效原因。旧通讯和来源任务保留，不改写其他稿件。保存相同正文、正常流式追加／续写保持缓存；独立有效的正文前通讯仍可复用。

手动编辑、保存和备份本身不会调用模型。手改后的分支再次明确生成时，不携带失效的正文后事实，按原阶段逻辑生成一批新的正文后通讯。本次浏览器实测恰增加一次；未改正文的正常续写仍零额外终端请求。

## 数据与兼容

没有新增持久化字段、数据库或备份版本，沿用既有 jobs.status／error 和 terminalTaskVersion:1。失效原因、状态和原事实随完整本地／云端备份往返；备份恢复与刷新不会重新激活失效投影，来源记录不会删除。旧格式与图片／密钥／日志排除策略未改。

浏览器通过真实 IndexedDB、完整备份编码与覆盖／撤销、实际下载文件后追加导入（重绑存档 ID）核查原有记录。新场景再执行手改→完整备份→覆盖恢复→刷新→续写，并同时检查浏览器正文请求和合成上游最终收到的事实，均不含旧批次。
