# 学院原生迁移：架构执行方案 v2.1

2026-11-03。根据用户对《方案-架构设计.md》v2.0 的逐项确认修订。

本文说明接下来应实现的目标，不代表目标已经完成或部署。原稿保留作历史参考；与本文冲突的选型、输出守门、自动封禁、界面重做及备份范围条款不再作为实施依据。

## 1. 用户已确认的六项决定

| 项目 | 执行决定 |
| --- | --- |
| 模型接口 | 只允许管理员控制的白名单服务。用户选择服务并填写自己的密钥；不能通过自填地址绕过白名单。 |
| 原生逻辑与占位符 | `{{char}}` 是原生角色名字宏；`«STVAULT:description»` 是原稿自定义标记，两者不同。读取私有设定的处理继续使用酒馆原代码，在服务器可信运行环境完成。不能仅靠最后字符串替换宣称完整兼容。 |
| 用户参数 | 模型、上下文长度、回复长度及原生支持的采样参数允许用户配置，不增加学院任意的小上限。实际 token 计算、模型容量和明确的服务资源保护仍需正常工作。 |
| 内容检查 | 服务器收到用户提交的请求后，检查强制索取私有设定的指令。命中则拒绝该次请求并显示原因；不实现原稿的输出 n-gram 相似度守门、累计违规自动永封。 |
| 输出方式 | 用户可以切换流式和非流式；两个路径都必须正常生成、取消、报错、过滤显式模型思考，并保持一致的保存结果。 |
| 原有要求 | 保留完整学院前端、CSS、功能、服务器存储、备份兼容和助手隔离要求。本文补充架构，不用新文档覆盖既有功能范围。 |

这些决定也不构成对外部软件安装或解除既有生成暂停的额外授权。服务器原生运行环境仍按此前明确选择处理，不能因写完方案就擅自启用。

## 2. 项目边界

- 新版是原学院页面连接酒馆原生后端与运行时。保留桌面及移动网页的 CSS、布局、加载动画和原有操作入口。
- 使用固定原版 SillyTavern 1.19.0，提交 `06bde939fb1e9c4c8d8641d810f0a916b5bce127`。原版跟踪源码保留，学院连接、权限与业务扩展放在明确的适配层。
- 原生 JSONL、swipes、设置、预设、世界书、资源与 Secrets 为主要基础；不另写更窄的提示词引擎或把旧 workspace 整包存到服务器就视为完成。
- 新版独立站为 8088；已批准的助手隔离环境为 8089。目录、账号、数据和服务与旧 8807/9000 分开。
- 只有一张固定学院世界卡，多个存档对应多个聊天。多 NPC、玩家人设库及终端联系人保留；“固定一张世界卡”不等于删除自定义人设或限制剧情角色数量。
- 账号注册、邀请码和管理员管理沿用既有方向及原生账号机制；新增规则不得破坏已有账号和资料。用户自行新建其他角色卡不作为此固定世界站点的管理功能。

## 3. 总体数据流

```text
学院原前端
  ├─ 用户输入、人设、预设、世界书、参数及流式开关
  ├─ 公共剧情、变量、终端记录与页面交互
  └─ 调用受鉴权的学院／原生接口
             ↓
服务器
  ├─ 核验身份、数据所属账号、白名单服务及用户提交内容
  ├─ 读取服务器保存的聊天、资源和私有学院设定
  ├─ 可信环境调用固定酒馆原版：
  │    宏、预设顺序、对话示例、世界书扫描、上下文预算及正则
  ├─ 原生模型接口适配 → 白名单服务
  ├─ 流式或非流式响应：过滤显式模型思考、整理错误
  └─ 使用原生保存接口写回聊天、设置和学院扩展
             ↓
学院原前端显示公开结果
```

玩家脚本运行在独立助手环境，通过受控通信访问当前账号和会话允许公开的数据。它不进入含私有设定的可信编排环境。

## 4. 为什么不采用“最后替换一下就完成”

原版中的 `{{char}}`、`{{user}}` 等宏继续沿用原语义。它们不是访问隔离机制。

原稿的 `«STVAULT:... »` 属于自定义标记。即使最终替换成功，也不能恢复在替换之前已经丢失的处理结果：

- 对话示例要先按发言人和行拆成消息。只有一个标记时，原版可能解析不出示例消息，最终请求中没有可供替换的位置。
- 世界书可以匹配角色描述、性格、场景及深度提示。前端只看到标记时，这些匹配结果与真实设定可能不同。
- 宏、正则、上下文裁剪和扩展可能读取或改写字段。修改发生后，再替换原标记无法保证原生顺序和结果。

因此，凡需真实设定的步骤，均在服务器可信运行环境调用固定原版完成。普通用户浏览器和助手环境只接收公开投影及受限结果，不接收完整私有编排内容。

必要的公开字段标记可以保留作连接信息，但不作为另一套提示词引擎；不追加自写宏解析器或世界书扫描器来填补原生行为。

原生前端代码依赖 DOM。当前已有服务器私有运行器代码，是否能在目标系统安全、正确地启动仍需验收。此处是运行官方代码的环境要求，不能将其描述成仅添加一个占位符就能省略。

## 5. 白名单服务与用户配置

### 5.1 管理员配置

白名单由服务器管理，至少包含服务标识、公开名称、允许的协议／主机／端口／基础路径和允许使用的任务种类。实际服务地址从管理员配置读取；文档不猜测、硬编码或公开真实密钥。

- 模型请求、模型列表、测试连接、重试和独立终端调用都使用相同的服务器白名单判断。
- 客户端自填 URL、原生 reverse proxy、自定义请求头或参数不得把请求改发到白名单外。
- 不跟随到白名单外的重定向；白名单校验失败时在发出私有内容前停止。
- 向量服务若使用独立地址，需有独立且明确的允许项，不能误用文本接口冒充 embeddings。
- 白名单为空或目标未配置时，返回“服务未配置／不在允许范围”，不自动改用默认第三方服务。

### 5.2 用户配置

用户仍可选择白名单服务、填写密钥、选择服务支持的模型，以及设置上下文、输出长度、采样参数和流式开关。密钥优先使用原生 Secrets，与普通设置及备份分开保存。

不添加学院任意的 3000 字符、32000 上下文或同类窄限制。原生实际 token 预算和提供商返回的容量限制仍然成立；资源、格式、服务商错误须分别说明，不能统一归为“预设不兼容”。

参数根据实际任务和对应模型计算。不能仅携带一个固定 `__realTokens` 总数就认为所有模型、宏展开、重复引用和字段开关下的预算均正确。

### 5.3 保密边界

设定将发送给管理员认可的模型服务；白名单服务属于明确的信任范围。目标是阻止普通页面、文件接口和玩家脚本直接取得私有资料，不对模型改写、概括或剧情表达作绝对不可泄露承诺。

## 6. 用户请求检查

检查对象是用户提交的请求中可控的输入，包括需要参与本轮调用的用户文本、用户预设、世界书、人设及脚本请求。原生组装后可对其中的用户来源内容再作校验，但不因包含可信作者规则就误判用户。

检查发生在携带私有设定调用模型之前。识别明确索取隐藏设定、要求输出内部提示词或绕过访问边界的指令；正常角色扮演、用户公开世界书和剧情引用需有回归样本。

处理方式：拒绝当前请求，给出可理解的原因，保留用户输入和已有聊天；不扣除或清空人设，不覆盖存档，不触发模型重写和无限自动重试。

取消 v2.0 的下列内容：

- 对模型回复与设定原文做 n-gram 相似度比对。
- 累积相似度命中次数、二次永久封禁及其灰度观察流程。
- 依赖整段回复缓存后执行上述输出守门。

管理员原有的手动禁用／启用账号能力可以保留。输入检查与模型思考过滤是不同职责，取消输出相似度检查不等于取消思考过滤。

## 7. 流式、非流式与响应过滤

### 7.1 用户切换

在原 API 设置中提供明确的流式开关，接入现有配置，不另建一套不一致的配置来源。正文、终端等使用各自已选配置；本轮请求启动后记录所用配置，避免切换设置破坏正在进行的响应。

流式正常逐步显示；非流式在完成后显示。两者必须保持角色回复解析、状态提交、终端记录和原生聊天保存的一致性。

### 7.2 两条响应路径都处理

固定原版的 `forwardFetchResponse()` 用于多条流式路径，但非流式还有独立的解析与 `response.send()` 路径。只在前者插入过滤器并不能覆盖所有结果。

响应适配应根据实际提供商协议处理：

- 删除不应公开的 reasoning／thinking 等显式思考字段或分块。
- 在文本内容字段中处理原有约定的思考标签，不在完整 JSON 上做破坏协议的全局替换。
- 流式正确处理 UTF-8、跨网络分块、SSE 事件边界与结束事件；非流式正确处理完整 JSON。
- 保留公开正文、usage、finish reason、错误与取消语义；不能因过滤静默丢失正文或伪造正常结束。
- 不以首个网络 chunk 是否以 `data:` 开头作为唯一协议判断；无法识别的响应明确失败，不作为不受检查的原始流直通。
- 继续过滤实际返回的显式模型思考；不为了过滤而额外索取模型私有思考。

过滤器只承担思考字段与协议边界，不新增输出相似度审查，不要求等待完整正文才能放行。分块延迟和性能需要实测，不承诺固定 11 字符或小于 50ms。

### 7.3 错误与记录

保留真实错误类型、HTTP 状态和安全的服务商说明，不把所有 400／404／502 归结为令牌权限；服务商原始错误若含私有请求、认证头或 Key，不能直接透传。

中止、长度截断、格式无效和上游错误要区别显示。失败时保留已确认资料，部分结果按现有显式规则处理，不把失败当成功写入，也不无限调用模型自修。

## 8. 固定世界卡与会话

新增聊天复用一张固定学院世界资源，并创建不同的原生聊天文件。玩家人设库、主人设及用户自定义关系继续独立管理。

现有代码每个存档建立一个角色引用，尚未达到这个目标。迁移时必须：

1. 列出旧角色引用、JSONL、所有 swipes、学院状态及资源关联。
2. 形成完整恢复副本，再创建目标聊天并回读比对。
3. 校验原生消息、轮次、选中稿、终端房间与来源引用后，才切换存档索引。
4. 写入失败或并发冲突保留原引用和原文件，不在未验证前删除角色资源。

保护私有卡、纯图片缩略图及公开头像的访问边界。用户自己的头像／人设功能与私有作者卡权限分开处理，不用一刀切禁用全部图片或人设接口。

## 10. 酒馆助手与扩展隔离

酒馆助手固定 JS-Slash-Runner 4.11.3，提交 `0af421068e7c03b6b0a71b68feb79d201164edeb`。使用原版资产和真实菜单、脚本管理、事件、变量、消息与受控生成功能，不用占位图标代替实现。

- 8089 承载玩家脚本；通过校验来源及请求身份的通信桥访问 8088 当前账号和当前会话的允许操作。
- 8089 不持有模型 Key、私有作者卡、完整隐藏世界书或完整提示词。
- 只允许导出当前功能需要的公开资料；跨账号、过期会话、跨稿件和未经允许的读写均拒绝。
- 仅端口不同不等于 Cookie 隔离完成。8088 还须检查跨来源请求和会话归属，不能仅依赖脚本页不显示密钥。
- 玩家脚本不得在服务器私有编排页面执行；对原生 DOM 或私有数据有依赖的扩展须逐项说明支持范围。
- “保留生态”不写成未经验证的 100% 扩展兼容，缺失能力明确报告。

## 11. 服务器存储与完整备份

服务器原生账号数据是唯一持久化权威。浏览器只保留可丢弃缓存和待迁移旧副本；服务器保存失败不能显示为本地已成功保存。

统一备份采集入口接入 BackupArchive，覆盖五条路径：

1. 本地下载所有数据。
2. 上传到用户选择的云端仓库。
3. 导入下载文件。
4. 拉取云端并覆盖本地／当前账号资料。
5. 恢复覆盖前完整副本。

必须包含：全部存档、所有稿件与状态、完整人设库、主人设、关联引用、备注、备忘录、草稿、记忆、变量、全部终端记录、预设、世界书、正则、助手配置与持久化变量，以及界面设置。

运行日志和模型原始输出不备份；API／仓库密钥和作者私有资料不进入普通备份。云端继续排除本地图片和用户立绘，图片 URL 保留。完整本地导出与云端过滤使用同一采集模型，明确区分资源策略。

- 导入旧格式缺少新增附加资料时保留本机资料，不按空集合清除。
- 更换存档 ID 时同步重绑人设 `sourceSessionIds`、主人设引用、终端及其他关联。
- 无法识别的新版本或未接入字段须在写入前停止，不能静默忽略。
- 覆盖前先形成完整一致副本；写入失败、回滚、跨页面修改与跨设备冲突有明确保护。
- 管理员离线灾备与用户普通导出分开。账号库、邀请码、私有卡及服务器凭据不得混进用户下载或云仓库；私有资料如有内部灾备需独立权限，不能因为不对外导出就永远没有恢复手段。

详见项目 `docs/BACKUP_COMPATIBILITY.md`。每次增加持久化字段，都重核五条路径，不只测 sessions 往返。
