# 一张世界卡的叙事流程

SillyTavern 会把角色定义、场景、玩家人设、世界信息与聊天历史等组织进模型上下文，参见官方 [角色设计](https://docs.sillytavern.app/usage/core-concepts/characterdesign/) 和 [提示词说明](https://docs.sillytavern.app/usage/prompts/)。本项目沿用这种上下文组织方式，由一张世界卡涵盖多名 NPC。这里的“按剧情判断在场”是本项目的结构化状态约定，并不声称是酒馆默认的群聊选人算法。

1. 作者卡片在服务器私有 JSON 中。网页无作者人设／世界书编辑器和角色卡导入导出。
2. 玩家创建自己的 persona 和存档，不勾选 NPC。开局无确定在场人物，等待模型生成第一幕。
3. 玩家发送行动。网页提交当前行动、所选稿件的最近 12 轮历史、已检索到的最多 8 条本地记忆、当前公开 MVU、基础文字预设、论坛上下文和可选骰点。旧开局只在历史未截断时附上。
4. 服务器加入原角色与世界定义。现有提取资料较少，当前每轮加入整份固定资料；未实现完整世界书关键词触发、递归扫描或 token 预算系统。原事件池不加入上下文。
5. 模型先输出正文，再输出一个 `<SR_STATE>…</SR_STATE>` JSON 块，最后强制追加隐藏结束标记 `<SR_DONE>`。`presentCharacterIds` 必须是当前场景完整名单，允许空；不是增量名单。名字提及、回忆、远程通讯与发帖本身不表示在场。
6. 服务器流式转发正文，拦截状态块；校验角色 ID、重复 ID、字段和长度。把完整名单映射为每名已知角色的 `present` 更新，自动清除上一幕离场角色。允许 char 动态想法、已知精神体 OS 和有剧情依据的 user 身份更新；user 内心想法过滤；固定姓名／性别和好感度变更不接受模型覆盖。
7. 缺少完整状态或结束标记时，后台在同一次剧情流里从断点续写最多3次，保持原行动、骰点和接口，不能重新掷骰或开新轮。三次仍未完成才提示，可手动继续；主动停止立即停止后续调用。前端收到合法完成结果才提交一次状态、事件记忆和可选论坛动态。未完成或状态校验失败时保留正文、沿用上一轮状态，不提交记忆和新帖子。
8. 下一轮以所选有效稿件重建历史与状态，切稿／回退同步影响记忆和论坛。每 5 个有效事件可另调摘要接口，行动建议也由辅助任务产生；副模型未配置则用主模型。这些会产生额外模型请求。

现在使用项目自有的 MVU 适配层，没有执行模型输出的 JS，也不声称兼容完整酒馆 MVU 或脚本插件。正式变量路径与好感规则仍等作者提供。

## 模型连接

本机设置页填写兼容 Chat Completions 的基础地址、实际模型名、Key，再点击确认服务。服务地址通过本机会话登记；变更地址或模型需重新确认，导入备份不会自动获得连接许可。实际发出生成请求时才调用服务。URL 禁止内嵌凭据／查询参数／片段，拒绝重定向。Key 不保存在持久配置。

这只是维护者本机测试的连接方式，不能直接作为朋友共用的商业后台。公网部署时应把供应商地址、模型和密钥固定在服务端，朋友只登录和游玩；保留资料私有不等于可对模型输出作绝对保密保证。

骰子开启时，先校验D100与等级一致，再由服务器生成固定方向的 dicePlan。模型必须把事件落在本轮主线正文和 event 中，并在 diceEvent 返回 direction 与具体 description。缺失、格式不合或方向相反通过 SSE error 报告，不发 done、不提交状态。关闭时不得返回骰子事件。校验验证结构和声明方向，不能代替对整段自然语言效果的人工判断；未做额外付费模型审判。
